\section{Discussion \& Conclusion}
\label{sec:discussion-conclusion}

The chosen architecture, centering on a master-worker topology with HDFS and Apache Spark, proved highly suitable for the batch processing requirements of the NYC Taxi dataset. The combination of Parquet's columnar storage and Spark's in-memory computation successfully addressed the challenge of processing millions of records within the strict resource constraints of our OpenStack environment.\\

One of the most successful aspects of our implementation was our schema enforcement strategy. By bypassing global schema inference and implementing explicit type-casting for the volatile \texttt{Airport\_fee} column, we stabilized an otherwise fragile ingestion pipeline. Furthermore, our aggressive column pruning allowed us to maximize the utility of the 4~GB RAM per node, enabling the processing of 10~GB workloads that would have otherwise triggered memory exhaustion.\\

Our scaling experiments revealed that vertical scaling is more cost-efficient than horizontal scaling for this workload. Adding cores within existing nodes achieved 68\% efficiency on 10\,GB data, compared to 56\% for adding new worker nodes. This is because intra-node parallelism avoids the network overhead of cross-node data redistribution during the aggregation phase. However, both approaches achieved nearly identical per-resource efficiency ($\sim$56\%) on the smaller 5\,GB dataset, indicating that the advantage of vertical scaling emerges only when the workload is sufficiently compute-intensive.\\

Our further experiment on OS page caching impact showed that caching can dramatically alter benchmark results: ETL runtime dropped by 94.6\% (129s $\to$ 7s) and total pipeline time by 66\% when data blocks were served from kernel RAM. This highlights the importance of controlling for cache state in distributed systems benchmarking.\\

The most significant takeaway from this project is the non-linear nature of distributed systems. Adding more resources does not proportionally improve performance; the serial ETL fraction (Amdahl's Law, $f \approx 6.25\%$) and network communication overhead during data redistribution impose hard limits on achievable speedup. Effective data engineering requires managing the balance between data volume, hardware constraints, and framework overhead rather than simply scaling resources.
