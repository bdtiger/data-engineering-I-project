\section{Scalability Experiments \& Results}
\label{sec:scalability}
% ===========================================================================
\subsubsection{Experimental Design}
\label{sec:design}
% ===========================================================================
We evaluated the scalability of our Apache Spark data pipeline on an OpenStack SSC cluster composed of 4 \texttt{ssc.medium} VMs. The pipeline consists of two PySpark jobs: an \textbf{ETL job} (\texttt{etl\_job.py}) and an \textbf{Analysis job} (\texttt{analysis\_job.py})

We conducted three categories of experiments:

\begin{enumerate}
    \item \textbf{Horizontal Strong Scaling (H-1 to H-3):} Fixed data at 5\,GB, fixed cores per executor at 2. Varied worker nodes from 1 to 3.
    \item \textbf{Horizontal Weak Scaling (W-1, W-2):} Proportionally scaled both resources and data. 1 worker with 5\,GB, then 2 workers with 10\,GB.
    \item \textbf{Vertical Strong Scaling (V-1 to V-4):} Fixed workers at 3. Varied cores per executor from 1 to 2, tested on both 5\,GB and 10\,GB datasets.
\end{enumerate}

Each experiment was executed with \textbf{operating system page caching active}, meaning previously read HDFS data blocks remained present in the Linux buffer cache between runs. ETL and Analysis runtimes were measured independently using separated timestamps.

\subsection{Analysis of Results}
% ===========================================================================

\subsubsection{Constant ETL Phase}

The ETL job completed in 7--8 seconds regardless of configuration. This indicates that the ETL phase is not compute-bound, adding more workers or cores has no effect on ETL. 

\subsubsection{Horizontal Strong Scaling}

Adding workers from 1 to 3 reduced the total runtime from 128s to 76s (1.68$\times$ speedup), with the Analysis phase improving from 120s to 69s (1.74$\times$). Scaling did work, but fell well short of the ideal 3.0$\times$.

The possible causes are:
\begin{enumerate}
    \item The ETL phase (7--8s) is serial and unaffected by parallelism. 
    \item The \textbf{groupBy aggregation} in the Analysis job requires data to be redistributed across workers. This overhead grows with the number of workers.
\end{enumerate}

\subsubsection{Weak Scaling}

Weak scaling produced an interesting result. Doubling both workers (1$\to$2) and data (5\,GB$\to$10\,GB) changed runtime from 135s to only 91s. In an ideal weak scaling scenario, runtime should remain constant. Here, surprisingly, runtime actually \textit{decreased} by 33\%. The weak scaling efficiency is 74.2\%, well above the 50\% threshold.

The possible reason is that with 2 workers, the per-node data volume is similar, but Spark gains additional 2 cores. This might allow better computation performance
\subsubsection{Vertical Scaling}

Vertical scaling (adding cores within the same worker nodes) yielded markedly different results depending on the dataset size:

\begin{itemize}
    \item \textbf{5\,GB (V-1$\to$V-2):} Modest improvement from 80s to 72s (1.11$\times$ speedup, 55.6\% efficiency). With 3 workers already providing baseline parallelism, adding a second core per executor doubles cores from 3 to 6. However, the 5\,GB dataset is small enough that the additional concurrency yields diminishing returns.
    \item \textbf{10\,GB (V-3$\to$V-4):} Stronger improvement from 102s to 75s (1.36$\times$ speedup, 68\% efficiency). The larger dataset provides enough computational work to utilize additional cores. It suggests the 10\,GB workload is sufficiently compute-intensive to benefit from vertical scaling.
\end{itemize}

% ===========================================================================
\subsection{Horizontal vs. Vertical Scaling Comparison}
% ===========================================================================

\textbf{Comparing Horizontal vs. Vertical scaling reveals a critical insight for this workload.} 
For the 5\,GB dataset on our ssc.medium cluster:

\begin{itemize}
    \item Horizontal scaling (H-1$\to$H-3): 1.68$\times$ speedup, 56.1\% efficiency.
    \item Vertical scaling (V-1$\to$V-2): 1.11$\times$ speedup, 55.6\% efficiency.
\end{itemize}

At first glance, horizontal scaling appears superior (1.68$\times$ vs 1.11$\times$). However, Horizontal scaling tripled resources ($p=3$) while Vertical scaling only doubled them ($p=2$). When normalized by efficiency, both achieved nearly identical efficiency ($\sim$56\%). This means that each additional unit of compute resource provided the same marginal improvement regardless of whether it was added as an extra node or an extra core.

For the \textbf{10\,GB dataset}, vertical scaling achieved the highest efficiency of any experiment at \textbf{68\%}, compared to the horizontal experiment's 56\%. The reason is that adding a core within an existing worker avoids the network communication overhead that horizontal scaling introduces. When a new worker is added, intermediate aggregation results must be transferred across the network during the groupBy/join phases.

\subsection{Bottleneck Identification}
\label{sec:bottlenecks}
% ===========================================================================

\subsubsection{Bottleneck 1: Network Communication Overhead}
The Analysis job's \texttt{groupBy} aggregation requires data redistribution across workers. Each worker must send its local aggregation results to every other worker, which might generate network overhead.

\subsubsection{Bottleneck 2: Fixed Serial Overhead (Amdahl's Law)}
The ETL runtime of 7--8s is completely unaffected by parallelism. By Amdahl's Law, this  limits the maximum achievable speedup with 3 workers. Additional serial costs (Spark  initialization, HDFS metadata lookups etc) further increase this.

\subsection{Further Experiment: Impact of OS Page Caching: Cold vs.~Hot Cache}
% ===========================================================================

To quantify the impact of Linux OS page caching on benchmark validity, we executed the full experiment matrix under two conditions: (1) \textbf{Cold Cache} — the Linux page cache was purged via \texttt{sudo sh -c 'sync; echo 3 > /proc/sys/vm/drop\_caches'} before each run, forcing physical disk reads; and (2) \textbf{Hot Cache} — the page cache was left intact, allowing the kernel to serve HDFS blocks from RAM.

Table~\ref{tab:cold_vs_hot} shows a representative comparison using the \textbf{H-3} configuration (3 workers, 2 cores/executor, 5\,GB).

\begin{table}[htbp]

\label{tab:cold_vs_hot}
\begin{tabular}{lrrr}
\toprule
\textbf{Metric} & \textbf{Cold Cache (s)} & \textbf{Hot Cache (s)} & \textbf{Reduction} \\
\midrule
ETL Runtime          & 129 & 7   & 94.6\% \\
Analysis Runtime     & 96  & 69  & 28.1\% \\
Total Runtime        & 225 & 76  & 66.2\% \\

\end{table}
