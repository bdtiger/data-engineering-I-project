\section{Question 1: Batch vs. Streaming Processing}

From a problem perspective, the choice between batch and stream processing is dictated by the nature of the data and latency requirements of the application. Batch processing assumes the existence of static, bounded datasets where all input data are available before the computation begins\cite{computers3040117}. This is necessary for scenarios where system throughput and computation is preferred over system latency, such as training language models, analyzing large scale documents where maximizing overall system output and robust fault tolerance are more critical than response time. On the other hand, streaming processing is required for continuous and unbounded data such as server log monitoring, internet-of-things (IoT) sensor outputs or social media where analytics need to be performed continuously in real-time. For example, Twitter uses real-time streaming to measure real-time active user count (RTAC) indicator to find user engagement events\cite{10.1145/2723372.2742788} where low latency is a strict necessity.


Early batch frameworks like Google's MapReduce \cite{dean2004mapreduce} achieved massive scalability and fault-tolerance by using high-throughput disk-based storage. While this ensures reliability against machine failures, it incurs significant disk I/O latency overhead, making the framework unsuitable for real-time queries. To tackle the latency issue, Apache Storm was introduced, which process data one at a time using a directed graph\cite{10.1145/2588555.2595641}. To address the limitations of Storm, Twitter developed Heron which adopted a one task per JVM model to achieve process isolation and a backpressure mechanism. However, early streaming systems often traded off the consistency and high throughput characteristic of batch processing systems making the latter still relevant.

Some recent frameworks have been developed to connect the gap between batch and streaming processing by unifying the architectural division. Apache Spark approaches this unification through "micro-batching", dividing the continuous streams into small batches to leverage fault-tolerance and in-memory batch execution\cite{computers3040117}. While Apache Flink took the inverse approach by treating batch processing as streaming processing where data stream is considered finite\cite{df177547a4364bb0a7e2470b83025bb0}. Further bluring the lines between the two paradigms, abstraction model like Apache Beam \cite{li2018challenges} allows programmer to write unified and portable data processing pipelines that can be executed on either batch or streaming processing engines.

Finally, the Dataflow Model\cite{10.14778/2824032.2824076} serves as the definitive framework for unifying batch and streaming processing to achieve batch processing correctness within a streaming processing environment. Ultimately, the model suggests a  trade-off between correctness, latency, and cost, allowing a single pipeline to produce both low-latency high-accuracy results, effectively treating batch processing as a specific instance of streaming where the data source happens to be finite.
